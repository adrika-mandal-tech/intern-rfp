01

The problem statements driving the implementation

Business problem

The core challenge is that procurement teams are drowning in repetitive, high-stakes document work. An incoming RFP may contain hundreds of requirements, many of which are already answered somewhere in a company’s previous work. But blindly reusing old content creates a serious risk: a proposal is a binding commercial document, and a confident but unsupported answer can become a real commitment.

Technical problem

The system must not only retrieve relevant text, but also decide whether that text truly answers a requirement. Similarity alone is not enough. The project therefore focuses on evidence selection, safe refusal, citation verification, and human review for sensitive content.

Where the numbers stand today

622Requirements in the reference RFP — 50 of them (8%) are covered by the golden set
12Verified negatives. The entire safety measurement rests on these twelve rows
1Real pair owned. Every finding the project has comes from it
0Invalid citations measured so far — an existing result to protect, not a target to reach

What this work is meant to move

~3×Target safety sample — the number of verified negatives available to test refusal
25+Sources checked for real RFP-proposal pairs, dead ends included
2Research memos feeding an open product decision
02

Implementation principles

These are standing rules that apply to every phase, not stages with a status. They are the house style: work that follows them is reviewable, and work that does not is unusable no matter how much of it there is.

R1

Evidence before assertions

Every claim must be traceable to the actual document and page, not just a plausible answer. A self-report is a claim, not a verification — including my own.

applies throughout
R2

Measure what matters

Do not optimize a metric that cannot detect false answers. Before trusting a number, ask what would make it go down — a golden set with no verified negatives in it cannot fail.

core evaluation rule
R3

Record reasoning

Every judgment must include the reason behind it so others can review and challenge the conclusion. Reasoning that is not written down cannot be checked, and the row becomes unusable.

makes work auditable
R4

Safe refusal is first-class

The system should prefer “I cannot determine this from the available evidence” over an invented answer. The same standard applies to my own deliverables: “I don’t know, here is what I checked” is a complete answer.

product safety principle
R5

A safety rule that over-fires is not safe

Refusing everything protects nobody, because a tool that refuses half the time gets switched off. Never assess what a rule catches without also assessing what it breaks.

counterweight to R4

Phase 0 — Overall stack and tools required across the project

Foundation layer

This phase is not a delivery task in itself, but it defines the operating system for every later phase. The work depends on a small and deliberately boring stack: Python (standard library only) for validation, JSONL for structured evidence rows, Markdown and HTML for documentation and presentation, and a PDF viewer for the source documents. Nothing here needs an account, an API key, a running server, or a network connection.

Core tools and why they matter

  • Python — runs the three scripts that ship with the pack: verify_quotes.py (daily self-check), make_worklist.py (already run), extract_pages.py (already run).
  • JSONL — the row-level format for annotations: verdict, page, quote, reasoning. One object per line, so files diff and merge cleanly.
  • Markdown / HTML — research memos, logs, and presentation-style deliverables.
  • PDF viewer — the primary research instrument for Phase 1. Page numbers always mean the viewer’s page counter, never the number printed in the footer.
  • Public-source research workflow — browser plus a disciplined log, for Phases 2 to 4.

Setup gate before Phase 1 begins

Phase 1 cannot start until this command runs and reports 41/41 verified:

python tools/verify_quotes.py --claims 02-evidence/example_annotations_C.jsonl

That single command re-checks 50 real annotations against 214 pages of PDF text. If it does not produce that output, the daily self-check in Phase 1 will not work either, and it is worth raising immediately rather than annotating blind.

Key challenge this phase hits

Tooling fragmentation is a real risk in this kind of work. If the workflow is not standardized, evidence becomes hard to compare, review, and trust. This phase reduces that risk by creating a shared operating model for the entire project.

Phase 1 — Expand the golden set

Objective

Build a stronger evaluation ruler by adding more hand-verified examples to the golden set. The value of this work is not annotation volume; it is increasing the number of verified true negatives that can test whether the system refuses appropriately. Target: 60 rows — 40 from the fair sample, 20 from the lockbox-biased sample.

Implementation points

  • Step 1. Review the existing annotation examples and the task brief so the labeling style is consistent.
  • Step 2. For each requirement, note what it actually asks and which service line it is scoped to — that scope decides the hardest calls.
  • Step 3. Search the proposal, then decide answered, partial, or none by the decision rules below.
  • Step 4. Capture a verbatim quote (25 characters minimum, pasted not retyped), the page number from the viewer’s counter, and a short reasoning note.
  • Step 5. Keep the two worklists separate: one fair sample, one lockbox-biased set designed to stress the gap problem. Never report a combined rate.
  • Step 6. Run the verification script daily to catch quote and page mismatches before they accumulate.

The decision rules — the part that makes a row valid

These are the rules a human adjudicator already applied to resolve the disagreements in the existing 50 rows. Applying the same ones is what makes new rows mergeable with the old set; labelling by instinct instead produces 60 rows that cannot be combined with anything.

RuleWhat it saysWhy it is that strict
1 · Service line A requirement scoped to a service the vendor did not bid is none, even when the same capability is described elsewhere for a different service. This exact substitution is the system’s dominant failure mode. If the golden set blesses it, we score the system for doing the thing we most need it not to do.
1b · Headings A differing section heading is not a scope problem. Only the requirement’s own scope decides Rule 1. RFP and proposal headings come from unrelated taxonomies and nearly always differ. A shipped rule that treated this as meaningful began refusing 18 of 38 answerable requirements.
2 · Staleness Answered but out of date is still answered — old names, old figures, “available in the fall of 2018”. We are measuring whether the library contains an answer, not whether it is publication-ready.
3 · Exhibits An answer that exists only as a pointer to an exhibit not in the document is partial. We measure what is findable in the text we actually have.
4 · No rule fits Do not force a verdict. Record best judgement, set confidence low, explain the tension, and flag it. The existing set has five such rows and each exposed a real definitional question about the product. A flagged ambiguity is a finding, not a failure.
none rows carry page: 0 and an empty quote. You are asserting an absence, so there is nothing to quote — and the checker rejects a none that carries one. These are the most valuable rows in the set; state them plainly when they are true.
Failure mode to avoid

Resolving every hard call as none to feel safe. That produces a golden set which rewards a system for refusing everything, which is principle R5 broken from the annotation side. Be strict exactly where Rule 1 says to be strict, and honest everywhere else.

Key challenge this phase hits

Ground-truth scarcity and annotation drift are the main risks here. Without enough verified negatives, the system can appear safe simply because the evaluation set contains too few true gaps.

  • Problem statement: the project needs reliable negatives, not just positive examples.
  • Why it matters: it creates the evidence needed to make the safety metric meaningful.
  • Why a human must do it: a golden set produced by the system under test measures the system against itself and scores near-perfect while proving nothing.

Definition of done

  • All 40 rows of list A and all 20 of list B carry a verdict, confidence and reasoning.
  • verify_quotes.py reports zero not_found and zero empty_quote on both files.
  • Every none row has page: 0 and an empty quote.
  • A summary written per the template: verdict counts per list, reported separately, low-confidence count, rows wanting a second opinion, and any traps not already documented in the brief.
This phase is fundamentally about creating a trustworthy ruler before using it to score the system.
05

Phase 2 — Source real RFP-proposal pairs

Objective

Find more examples of a real RFP and a real proposal submitted in response to it. This is the most valuable external expansion because the current system is anchored to a single real document pair.

This phase may not find a pair, and that is a planned outcome

Genuine submitted proposals are scarce by their nature — commercially sensitive, rarely published, hard to obtain. A prior search across banking and finance produced exactly one. Success here is tiered, and the lower tiers are real deliverables, not consolation prizes. What would make this phase fail is a week of searching that produces nothing another person can read.

TierWhat was foundWhy it counts
AA genuine submitted proposal and the RFP it responds toThe goal. Even one roughly doubles the project’s evidence base.
BA genuine submitted proposal, RFP not findableStill usable as knowledge-base material.
CA source that publishes received proposals — a portal, agency or records archive — even with no pair extracted yetOften worth more than a single document. A repeatable source yields many pairs; one lucky find yields one.
DA documented list of places that do not work, and whyStops the next person spending a week rediscovering it. A specific negative is a finding.

Implementation points

  • Step 1. Target publication habits, not documents. The one pair we own exists because Delaware proactively publishes the proposals it receives. The highest-value find is another agency with that habit, because it yields many pairs rather than one.
  • Step 2. Work the reverse direction: proposals are rare and RFPs are everywhere, so start from a proposal and use the solicitation number printed in its first pages to find the matching RFP. Starting from an interesting RFP and hoping its proposals exist is the slow direction.
  • Step 3. Verify whether each candidate is truly a submitted proposal rather than a template, brochure, or sample response — vendor voice, named buyer, specific solicitation number, answers in order.
  • Step 4. Confirm the file is what it claims: a real proposal is megabytes, not kilobytes. Some government servers return an HTML block page saved under a .pdf name.
  • Step 5. Record the RFP identifier, vendor, buyer, page count, and classify by the tier table above.
  • Step 6. Log every source checked as you go, dead ends included, specifically enough that a reviewer can rely on the negative instead of repeating it. “Publishes RFPs and award notices but no received proposals; checked 12 solicitations across 2023–2025” is a conclusion. “Nothing there” is not.

Key challenge this phase hits

Data access and trust are the main obstacles. Real proposals are commercially sensitive, and public access is inconsistent, so success depends on finding publication habits rather than chasing one-off documents.

  • Problem statement: the project needs realistic evaluation examples, but real pairs are hard to procure.
  • Why it matters: this phase determines whether the system can be evaluated on genuine RFP-response behavior, or only on one document.
  • Boundaries: public and freely accessible documents only — no sign-ups, payments, records requests, or misrepresentation to obtain a file.
06

Phase 3 — Questionnaire landscape

Objective

Investigate whether the product should expand from RFPs into the question-driven world of questionnaires such as SIG, CAIQ, and DDQ. This is a strategic evaluation rather than a drafting task, and it feeds a decision that is genuinely open.

Implementation points

  • Step 1. Collect real examples of common questionnaires and observe their structure, format, and question style — question counts and quoted samples, not descriptions.
  • Step 2. Compare them to RFPs on stated dimensions: are questions pre-listed or buried in prose? Are answers free text or constrained? Does the output shape match what our system drafts?
  • Step 3. The decisive question. Determine whether completed questionnaires — real answers from real companies — are obtainable, or whether only blank templates are. Only the completed ones are a knowledge base.
  • Step 4. Evaluate whether that data could support a golden set with verified gaps in it. A curated answer set with no true negatives is answerable by construction and would score near-perfect while measuring nothing.
  • Step 5. Conclude whether the pivot argument holds — including the outcome where the honest answer undercuts it.
Research discipline

Do not ask leading questions of the evidence. “Are questionnaires simpler and easier to ground?” presupposes its answer; “what is the question format, and is completed data obtainable?” does not. The first version finds support for a pivot whether or not one is warranted.

Most first-page results will be marketing from companies selling questionnaire-automation software. Their figures are sales material until independently sourced — use them as leads, label them as vendor claims, and find the practitioner’s version.

Key challenge this phase hits

Market fit uncertainty is the central challenge. The question is whether the market offers enough completed, grounded questionnaire data to create a meaningful benchmark — otherwise the product argument becomes much weaker.

  • Problem statement: the product may need to stay focused on RFPs if completed questionnaire data is as scarce as real proposals.
  • Why it matters: this phase informs whether the roadmap should expand or stay narrow.
07

Phase 4 — Competitor landscape

Objective

Understand what competitors already do, what they claim, and most importantly what they do not appear to solve. This phase aims to identify whether there is a genuine market gap around safe refusal and evidence-led drafting.

Implementation points

  • Step 1. Catalog prominent RFP-response tools and AI-native providers.
  • Step 2. Extract what each claims about retrieval, answer generation, citations, and human review — quoting the actual claim.
  • Step 3. Compare their positioning to the project’s central differentiator: controlled gap detection and safe refusal.
  • Step 4. Establish whether anyone publishes measurements — accuracy, refusal rates, citation validity — or whether the whole category is unquantified claims.
  • Step 5. Establish whether anyone does requirement mining from raw prose, or whether every tool assumes the user supplies a clean question list. Either answer is decision-relevant.
  • Step 6. Translate the research into a sharp product thesis rather than a generic market summary.
Reporting discipline

Keep “X says it does this” and “X does this” visibly separate throughout. A product page supports the first and almost never the second. Do not assess a competitor’s quality — you have not used the product. Report what they claim and, more usefully, what they are silent about: a page that discusses speed and content libraries at length and never mentions accuracy, citations or review is telling you what its buyers are not asking for.

Key challenge this phase hits

Positioning and differentiation are the real challenge. Many vendors talk about answer libraries and speed, but far fewer treat gap detection, refusal behavior, and traceability as core product capabilities.

  • Problem statement: the product needs a sharper thesis than "faster drafting."
  • Why it matters: this phase shapes the narrative for why the solution is defensible.
08

Phase 5 — Explainer review

Objective

Review the project explanation from the perspective of a new teammate or stakeholder. The purpose is not to find typos, but to identify where the story is confusing, incomplete, or overly technical.

Pass 1 is time-critical and cannot be rescheduled

This phase is two passes, not one, and the first one has to happen immediately — while the explainer is still unfamiliar.

Pass 1 (now): read the explainer and keep a running note of every point of confusion, re-read, or unknown term. Raw, unedited, in reading order. Ten minutes of work.

Pass 2 (at the end): re-read knowing the project, and assess accuracy, gaps, structure and diagrams.

Why the order matters: once you understand the project you can no longer see what was confusing about it — you read straight past the gap. This is the only deliverable in the whole plan that becomes impossible rather than merely late. If the explainer has already been read once, write down whatever confusion is still remembered, today, and mark it as reconstructed.

Implementation points

  • Step 1. Pass 1 — capture first-read confusion as it happens, before looking anything up.
  • Step 2. Pass 2 — check the explainer’s claims against the evidence documents. Any number that contradicts them is a defect, not a suggestion, and gets reported separately and first.
  • Step 3. Note where the problem, workflow, or decision logic becomes unclear, and where definitions arrive later than the terms they define.
  • Step 4. Assess whether the diagrams carry meaning or decorate — a diagram that needs the surrounding text to explain it is not working.
  • Step 5. Review the intern pack itself: was the reading order right, were the briefs specific enough, and what had to be asked of a person that should have been written down? Each of those is a defect in the pack.
  • Step 6. Produce a memo: pass 1 notes verbatim, pass 2 findings grouped, accuracy defects first, then the top five changes ranked.
Specific beats polite. “Section 4 lost me at the second paragraph — I did not know what ‘grounding’ meant and it was not defined until section 7” is worth more than three paragraphs of balanced assessment.

Schedule, checkpoints and escalation

A plan needs quantities and dates, not only a method. This section is what turns the phases above into something whose progress can be checked mid-week rather than judged at the end.

DaysWorkCheckpoint
1Orientation reading; setup gate; Phase 5 pass 1Verifier prints 41/41. Pass 1 notes exist.
2Phase 1 — first 5 rows only, then stopHard gate: run the verifier and read every result before annotating a sixth row.
3–5Phase 1 — approximately 12 rows/dayVerifier clean at end of each day. Rule-4 flags logged as they arise.
6–7Phase 1 — finish 60 rows; write the summaryZero not_found. Counts reported per list, separately.
8–10Phase 2 — sourcingEnd of day 9: if nothing in tiers A–C, raise it rather than continue the same approach.
11–12Phase 3 or Phase 4, whichever looks more useful by thenMemo drafted with sources cited as collected, not reconstructed.
13–14Phase 5 pass 2; finish outstanding write-upsAll deliverables reviewable without asking the author questions.

Escalate — do not absorb

  • Stuck more than half a day on the same thing.
  • A single annotation row eating more than 20 minutes — mark it low, log why, move on.
  • Two days into Phase 2 with nothing in tiers A–C.
  • A decision rule does not cover a case that keeps recurring — that means the rule is incomplete, which is a finding we want, not a personal gap.
  • Anything in the pack appears wrong. Write it down either way; never silently correct it.

Delivery shape and success criteria

  • Annotated evidence rows with verdicts, quotes, pages, and reasoning — 60 rows across two lists kept separate.
  • Source-candidate log covering 25 or more sources, successful and failed alike, plus a findings memo built around which sources publish received proposals.
  • Research memos on questionnaire data availability and competitor positioning, with facts and interpretation in separate sections.
  • A daily log and a running questions list, started on day one.

Success definition

The work is successful when each phase produces something that another person can inspect, trust, and build upon without needing to reconstruct the reasoning from scratch. Every deliverable states what was measured, on what data, at what sample size — and says plainly what could not be determined.

Failure modes to plan against

Four ways this work can be done diligently and still produce nothing usable. Each one is cheap to avoid at the start and expensive to repair at the end.

1 · Sixty rows that cannot be merged

The existing 50 golden-set rows were adjudicated by the four decision rules in §04. New rows labelled by instinct instead — however carefully — describe a different standard, so they cannot be combined with the old ones and cannot be scored together. The work would be real and the output unusable. Read the rules before the first row, not after the twentieth.

2 · A successful search reported as a failure

Genuine submitted proposals are scarce by nature; a thorough search can legitimately end with no pair. Without the tier model in §05 stated up front, that outcome reads as nothing achieved — when a documented map of which sources publish received proposals is a reusable asset the project does not currently have. Decide what counts as success before searching, or the result gets judged by the wrong standard.

3 · A deliverable that expires

The first-read review in §08 is the only item here that becomes impossible rather than late. Once the project is understood, its explanation stops being confusing — you read straight past the gap that a newcomer would fall into. Everything else in this plan can slip a day. This cannot.

4 · Evidence gathered to confirm what was expected

  • Leading questions. “Are questionnaires simpler and easier to ground?” presupposes its answer and will find support for a pivot whether or not one is warranted. Ask what the format is and whether completed data exists.
  • Vendor claims read as facts. A product page supports “X says it does this”, almost never “X does this”. Keep the two visibly separate.
  • Existing results read as targets. The zero invalid citations already measured is a property to avoid breaking, not a goal to reach — treating it as a goal hides that it is already true and could regress.
  • Over-correcting on safety. Principle R5 exists because refusing whenever unsure is not caution, it is a different failure. On this project a safety rule written that way rejected 18 of 38 answerable requirements before anyone noticed.

The three ideas worth carrying through every phase

Similarity cannot establish answerhood — text can be densely about a topic and still answer nothing, which is why a human reading the document is the only reliable source of ground truth. Safe refusal is the product, not a feature attached to it; everything measured here exists to test that one property. And a metric with no way to fail is not a measurement — which is why the verified negatives, the fair-versus-biased worklist split, and the documented dead ends all matter more than they look.
