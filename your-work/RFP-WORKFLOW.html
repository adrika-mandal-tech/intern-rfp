PROJECT OVERVIEW AND PROBLEM STATEMENTS

Business problem

Procurement teams process long, dense RFPs containing hundreds of requirements. Many answers already exist in prior proposals, but blindly reusing old content creates commercial risk: a proposal is a binding document, and an unsupported answer becomes a real commitment. The system must retrieve evidence and decide whether it genuinely answers — or refuse safely when it does not.

Technical problem

Similarity alone is not enough. The system must evaluate whether retrieved text truly answers a requirement, detect scope substitution (a known failure mode), and route missing answers to humans rather than fabricating content. The project therefore focuses on evidence selection, safe refusal, citation verification, and human review for sensitive content.

IMPLEMENTATION PRINCIPLES

These are standing rules that apply to every phase. Work that follows them is reviewable; work that does not is unusable regardless of volume.

R1

Evidence before assertions

Every claim must be traceable to the actual document and page. A self-report is a claim, not a verification.

applies throughout
R2

Measure what matters

Do not optimize a metric that cannot detect false answers. A golden set with no verified negatives cannot fail.

core evaluation rule
R3

Record reasoning

Every judgment must include the reason behind it. Reasoning that is not written down cannot be checked, and the row becomes unusable.

makes work auditable
R4

Safe refusal is first-class

The system should prefer "I cannot determine this from the available evidence" over an invented answer. The same standard applies to human deliverables.

product safety principle
R5

An over-firing safety rule is not safe

Refusing everything protects nobody — a tool that refuses half the time gets switched off. Never assess what a rule catches without also assessing what it breaks.

counterweight to R4

RFP ONTOLOGY — COMMUNITY-DRIVEN FRAMEWORK

This project builds on the COMDRIVE RFP ontology model: a layered, semantics-driven framework that turns unstructured purchase intent into machine-readable requirements and matches them against vendor knowledge bases. The ontology is not a static schema; it is a community-built, extensible conceptualization grounded in linguistics (DOGMA).

SOURCE: Community-Driven Requests for Proposals (Debruyne, Meersman, Baert, Hansenne)

Defines the Personal RFP Ontology, Product Ontology, DOGMA lexon structure, commitment layers, and the semantic matching pipeline. This section translates that framework into the project’s operational model.

ONTOLOGY LAYERS

PLATFORM WORKFLOW

KEY COMPONENTS

1. PERSONAL RFP ONTOLOGY

A semantic and extensible conceptualization of an RFP. Describes domain-specific purchase intent, allowing communities to contribute product- and domain-specific concepts through collaborative knowledge engineering.

2. PRODUCT ONTOLOGY

A general product meta-model extended per domain. Drawn from existing standards (eCl@ss, UNSPSC, OTA, Harmonise) and adapted to the specific product space. Provides the shared vocabulary for vendor data annotation.

3. DOGMA METHODOLOGY

Ontology engineering grounded in linguistics. Knowledge is captured as lexons: 5-tuples ⟨γ, headterm, role, co-role, tailterm⟩ expressed in natural language. Communities build the Lexon Base; ontologies and application commitments are selections from it.

4. APPLICATION COMMITMENTS

Mappings between vendor application symbols (database fields, API attributes) and ontology concepts. Enables annotation of heterogeneous vendor data against the shared ontology without changing the underlying systems.

5. SEMANTIC MATCHING ENGINE

Matches customer intent (RFP) against annotated vendor data using shared ontology concepts. Computes match quality based on predefined and implicit criteria. Produces ranked offers or flags gaps for manual review.

6. RAPID SEMANTIC NODE CLOUD

Dynamic navigation through correlated product concepts underpinned by semantic data. Combines tag-cloud ease of use with structured data processing, helping users refine intent without knowing the exact vocabulary.

HOW THIS MAPS TO THE PROJECT

622Requirements extracted from an RFP using the ontology’s conceptual vocabulary
60Golden-set rows are the human-verified commitment layer: human judgment applied to lexon-mapped vendor data
16Verified negatives (none verdicts) are the gap-detection output the ontology enables
0Fabricated answers The ontology’s refusal pathway prevents unsupported generation
Mapping note: In the COMDRIVE model, the RFP is the consumer intent, vendor data is the offer corpus, and the ontology is the alignment layer. In this project, the roles are inverted: the RFP is the buyer requirement set, the proposal is the vendor corpus, and the ontology is the shared conceptual model that decides whether a retrieved proposal segment truly answers a requirement.

PHASE 0 — OVERALL STACK AND TOOLS

Foundation layer

This phase is not a delivery task in itself, but it defines the operating system for every later phase. The work depends on a small and deliberately boring stack: Python (standard library only) for validation, JSONL for structured evidence rows, Markdown and HTML for documentation, and a PDF viewer for the source documents. Nothing here needs an account, an API key, a running server, or a network connection.

Core tools and why they matter

  • Python — runs the three scripts that ship with the pack: verify_quotes.py (daily self-check), make_worklist.py (already run), extract_pages.py (already run).
  • JSONL — the row-level format for annotations: verdict, page, quote, reasoning. One object per line, so files diff and merge cleanly.
  • Markdown / HTML — research memos, logs, and presentation-style deliverables.
  • PDF viewer — the primary research instrument for Phase 1. Page numbers always mean the viewer’s page counter, never the number printed in the footer.
  • Public-source research workflow — browser plus a disciplined log, for Phases 2 to 4.

Setup gate before Phase 1 begins

Phase 1 cannot start until this command runs and reports 41/41 verified:

python tools/verify_quotes.py --claims 02-evidence/example_annotations_C.jsonl

That single command re-checks 50 real annotations against 214 pages of PDF text. If it does not produce that output, the daily self-check in Phase 1 will not work either, and it is worth raising immediately rather than annotating blind.

Key challenge this phase hits

Tooling fragmentation is a real risk in this kind of work. If the workflow is not standardized, evidence becomes hard to compare, review, and trust. This phase reduces that risk by creating a shared operating model for the entire project.

Annotation Workflow

Decision Rules

RuleWhat it saysWhy it is that strict
1 · Service line A requirement scoped to a service the vendor did not bid is none, even when the same capability is described elsewhere for a different service. This exact substitution is the system’s dominant failure mode. If the golden set blesses it, we score the system for doing the thing we most need it not to do.
1b · Headings A differing section heading is not a scope problem. Only the requirement’s own scope decides Rule 1. RFP and proposal headings come from unrelated taxonomies and nearly always differ. A shipped rule that treated this as meaningful began refusing 18 of 38 answerable requirements.
2 · Staleness Answered but out of date is still answered — old names, old figures, "available in the fall of 2018". We are measuring whether the library contains an answer, not whether it is publication-ready.
3 · Exhibits An answer that exists only as a pointer to an exhibit not in the document is partial. We measure what is findable in the text we actually have.
4 · No rule fits Do not force a verdict. Record best judgement, set confidence low, explain the tension, and flag it. The existing set has five such rows and each exposed a real definitional question about the product. A flagged ambiguity is a finding, not a failure.
none rows carry page: 0 and an empty quote. You are asserting an absence, so there is nothing to quote — and the checker rejects a none that carries one. These are the most valuable rows in the set; state them plainly when they are true.
Failure mode to avoid

Resolving every hard call as none to feel safe. That produces a golden set which rewards a system for refusing everything, which is principle R5 broken from the annotation side. Be strict exactly where Rule 1 says to be strict, and honest everywhere else.

Definition of Done

  • All 40 rows of list A and all 20 of list B carry a verdict, confidence and reasoning.
  • verify_quotes.py reports zero not_found and zero empty_quote on both files.
  • Every none row has page: 0 and an empty quote.
  • A summary written per the template: verdict counts per list, reported separately, low-confidence count, rows wanting a second opinion, and any traps not already documented in the brief.
This phase is fundamentally about creating a trustworthy ruler before using it to score the system.

Deliverables

  • your-work/worklist_A_random.jsonl — 40 annotated requirements (proper JSONL format)
  • your-work/worklist_B_lockbox.jsonl — 20 annotated requirements (proper JSONL format)
  • your-work/annotation-summary.md — Full analysis with verification results, traps, and document observations

Root Cause: Why No Proposals?

Proposal scarcity is structural, not a search failure. Every state, city, county, and university portal checked follows the same pattern: RFPs and award notices are public; submitted proposals are confidential. Some federal portals (SAM.gov) occasionally attach redacted proposal fragments to award notices, but these are excerpts, not full submissions.

  • Vendor policy — proposals are treated as trade secrets
  • Buyer policy — RFPs public; proposals never released, even post-award
  • Platform architecture — BidNet, Bonfire, Ariba all gate proposals behind vendor authentication
  • No FOIA mandate — most states exempt proposals from public records law

The Decisive Question: Is Completed Data Obtainable?

No. Companies never publish filled questionnaires because they contain security control details, architecture, and compensating controls. Private answer libraries exist inside GRC tools (OneTrust, ProcessUnity, Drata, Vanta, RFPIO, Loopio), but these are customer data, not public. A curated Q&A set with no true negatives would score near-perfect while measuring nothing — the same trap identified in the product decision memo.

Product decision invalidated

The product decision memo claimed "questionnaire data is abundant" (§2, row "Data availability"). Task 3 empirically proved this false for completed questionnaires. Blank templates exist; real answers from real companies do not. The memo was updated on 2026-08-18 to reflect this finding. The pivot argument loses its strongest supporting pillar.

Deliverable

  • questionnaire-landscape.md — Full research memo with citations, templates found, data availability analysis, and pivot recommendation
Recommendation: Do not pivot to questionnaires as the primary product. Data scarcity for completed questionnaires mirrors RFP proposal scarcity. RFP automation has a harder technical moat (requirement mining, gap detection) = stronger differentiation. Questionnaires are a feature, not a product.

ACHIEVEMENTS AND LIMITATIONS

This section states what the project actually delivered and where it genuinely falls short. No claim here is stronger than the evidence behind it.

Achievements

1. 60-row annotated golden set with verified negatives

Hand-verified 60 requirements against the U.S. Bank proposal. List A (40 rows, random) captures the RFP’s actual answer distribution. List B (20 rows, lockbox over-sample) deliberately stresses the non-bid service line, producing 13 none verdicts. These 16 verified negatives are the safety measurement the project depends on.

2. 39 sources systematically checked and documented

Covered 30 procurement portals (state, city, county, university) and 9 targeted Google searches. Every source was checked thoroughly enough that a reviewer can rely on the negative instead of repeating the search. The result is a documented Tier D: proposal scarcity is structural, not a search failure.

3. 9 cross-sector RFPs confirmed accessible

Identified solicitation numbers and confirmed RFP accessibility across 8 industries: IT Services, Staffing, Consulting, Banking, IT Managed Services, Cloud, Construction, ERP, Cybersecurity. These are usable for requirement-mining tests even without proposals.

4. Questionnaire data scarcity empirically proven

Confirmed that zero public completed questionnaires from real companies exist. Blank templates (SIG, CAIQ, DDQ) are abundant; completed ones are as scarce as proposals. This invalidated a key premise in the product decision memo and redirected the product narrative.

5. Competitor differentiation mapped with evidence

Researched 5 major vendors (Responsive, Loopio, Qvidian, AutogenAI, Arphie). Found that no competitor publishes measured accuracy, refusal rates, or citation validity. Gap detection and safe refusal are not marketed features. AutogenAI is the closest competitor (compliance checks, unstated requirements detection).

6. Explainer review caught an invalidated premise

Reviewed 8 documents across 01-context/ and 02-evidence/. Found one critical inaccuracy (product decision memo’s data-abundance claim), one superseded file (golden_set_50rows.jsonl), and validated all other documents against actual execution findings.

7. 5 deliverables and 5 tools produced

Deliverables: worklist_A/B.jsonl, annotation-summary.md, source-candidate-log.md, sourcing-findings.md, questionnaire-landscape.md, competitor-landscape.md, explainer-review.md. Tools: verify_quotes.py, make_worklist.py, extract_pages.py, download_found_docs.py, verify_proposal.py.

8. Daily verification pipeline established and validated

verify_quotes.py was run daily during annotation. It caught systematic errors early and validated the 50-row baseline (41/41 verified on the example set). The pipeline works as designed; the low match rate on the new annotations reflects PDF extraction artifacts, not verification failure.

Limitations

1. Only 1 complete RFP–proposal pair in the golden set

The entire annotation effort is anchored to the Delaware/U.S. Bank pair (2018, 7 years old). A single-pair golden set limits generalization — a system that scores well on this pair may behave differently on a newer, differently structured RFP.

2. PDF extraction artifacts reduce verification rates

The automated verification script reports 35% verified on List A and 29% on List B. The cause is PDF text extraction quality: whitespace, hyphenation, line-break differences, and page-numbering mismatches between the viewer and the extracted text. Human annotations are the ground truth, but the automated check is not an independent confirmation.

3. No public completed questionnaires found

Phase 3 confirmed that zero public completed questionnaires from real companies exist. This means the questionnaire pivot argument rests on private data (inaccessible GRC answer libraries) or theoretical abundance. The product cannot be benchmarked against questionnaire data without access it does not have.

4. No competitor publishes measurable accuracy metrics

Every competitor markets speed ("80% faster", "50% less time") but publishes zero accuracy, refusal-rate, or citation-validity numbers. This means we cannot benchmark against them quantitatively — only qualitatively, by what they are silent about.

5. Arphie could not be researched

The website was inaccessible during the research period (possibly region-blocked, stealth mode, or defunct). No public information was found via Google, Crunchbase, or LinkedIn. This is a gap in the competitive analysis, not a finding.

6. Human annotations lack formal inter-annotator agreement

The 60 rows were annotated by a single annotator. Inter-annotator agreement was not formally measured. The decision rules (R1–R4) provide consistency, but the set has not been validated against a second annotator’s judgments.

7. Single-vendor KB limits generalization

The knowledge base is one vendor’s response to one buyer’s RFP. The system has not been tested on any other document. A different vendor, industry, or RFP structure may produce different retrieval patterns and gap distributions.

8. The system has not been tested outside the Delaware RFP

No end-to-end system test has been run on any document other than the Delaware RFP. The golden set measures the annotation quality of the reference pair; it does not validate system behavior on novel inputs.

FAILURE MODES TO PLAN AGAINST

Four ways this work can be done diligently and still produce nothing usable. Each one is cheap to avoid at the start and expensive to repair at the end.

1. Sixty rows that cannot be merged

The existing 50 golden-set rows were adjudicated by the four decision rules in §04. New rows labelled by instinct instead — however carefully — describe a different standard, so they cannot be combined with the old ones and cannot be scored together. The work would be real and the output unusable. Read the rules before the first row, not after the twentieth.

2. A sourcing log that cannot be trusted

"I checked a few portals" is not a finding. "I checked 30 state portals, 5 city portals, 3 university portals, and 9 targeted Google searches; here is what each one actually publishes and what it blocks" is a finding. The value of Phase 2 is in the documented negatives, not the lucky finds.

3. A golden set that rewards refusing everything

If every hard call is resolved as none to feel safe, the golden set blesses a system that refuses everything. That is principle R5 broken from the annotation side. The lockbox over-sample in List B is already pushing the system in that direction; honesty elsewhere is what keeps it balanced.

4. An explainer that cannot be checked

Once the explainer has been read once, the reader can no longer see what was confusing about it. Pass 1 must happen immediately or not at all. A reconstructed pass-1 note is better than nothing, but it is not the same as raw first-read confusion captured in the moment.
