01

The problem, in plain English

Plain english

When a government department or a large company wants to buy services — banking, IT, staffing, consulting — they publish a document called an RFP (Request For Proposal). It is long, often 100+ pages, and it contains hundreds of questions the vendor must answer: "Describe your disaster recovery approach." "What fees apply to wire transfers?" "Provide biographical information for key personnel."

Answering one is a slog that takes a team weeks. And here is the thing: most of the answers already exist. The company has written dozens of proposals before. The disaster-recovery answer is sitting in a proposal from two years ago. The team is mostly hunting through old documents, copying, and adapting.

So the job is: read the new RFP, find the matching answers in the old proposals, draft them, and be honest about what is missing.

Technical

Formally this is retrieval-augmented generation with a compliance spine. Input is an RFP document; output is a compliance matrix — one row per requirement, each carrying a coverage verdict, a drafted answer, and citations to the source pages the draft came from.

The hard parts are not the drafting. They are enumerating the requirements completely (a missed mandatory item can disqualify a bid), knowing when the knowledge base genuinely cannot answer (inventing an answer is worse than admitting a gap), and never auto-drafting anything commercial or legal (an invented fee in a submitted bid is a contractual problem, not a quality problem).

The single rule everything else follows from

An honest "I don't know" is worth more than a plausible answer. A proposal is a contract document. If the system invents a certification the company does not hold, or a fee it does not charge, the damage is legal and commercial — not a bad user experience. Every design decision below traces back to this.

What the system actually does

Five steps. Each one is a place where it can go wrong, and each has its own safeguard.

Figure 1 — the loop, with the safeguard at each stage
Why the fork at step 2 exists

Anything about money or signatures is pulled out before the system even looks for an answer. Not because it could not draft one, but because a drafted fee is a number nobody has approved. A person writes those. This costs a reviewer a few minutes; the alternative costs a contract.

03

The two documents — the bit people get backwards

There are always two documents in play, and confusing them produces a system that searches the RFP for answers to the RFP.

Figure 2 — one document is ingested, the other never is
Plain english

The old proposal is the library — it gets loaded into the system so it can be searched. The new RFP is the list of questions — it is read to work out what to ask, but never added to the library.

If you loaded the RFP into the library too, the system would happily "answer" a question by finding the same question written in the RFP. Confident, well-cited, and completely useless.

Technical

Ingestion writes chunks, embeddings and a tree index into a namespace that retrieval searches. Mining calls the sidecar's ParseDocument to get per-page text and never touches the store. The endpoints reflect this: POST /rfp/mine takes a file path and returns requirements; POST /unstructured/ingest is a different operation entirely.

Why this specific pair of documents

RFPs are published everywhere. Submitted vendor proposals almost never are — they are confidential and unindexed. We searched hard and found essentially nothing, until we discovered that the State of Delaware publishes the proposals it receives.

What we got is better than a topical match. U.S. Bank bid TRE18101-BANKINGSVC in 2018; TRE25101-BANKINGSVC is the 2025 re-bid of the same contract by the same buyer. Delaware even recycled its questionnaire almost word for word — which is exactly what real buyers do.

This is not an approximation of the use case — it is the use case: a vendor re-bidding work it previously won, using its old proposal as the knowledge base.
04

Why build it inside Grasph

Plain english

We could have built this as a standalone tool. We did not, because Grasph already does most of the hard, boring parts: reading PDFs including scanned ones, splitting them sensibly, turning text into something searchable, searching it well, talking to language models, tracking what it all costs.

Building those again would take months and produce something worse. What Grasph does not have is anything about RFPs — and that is exactly the part worth our time.

What the product needsGrasph already has it?

One rule this buys us, worth protecting

Every model call goes through EmbeddingService, which already supports OpenAI, Ollama and vLLM. That means "can our data go to an external API?" is a configuration question, not a rebuild. If the answer ever becomes no, we point it at a self-hosted model and carry on.

A single direct HTTP call to an API anywhere in our module would quietly forfeit that. It is written into the module docs as a rule that must fail code review.

05

Phase 0: building a ruler before measuring anything

Plain english

Before building the real thing, we spent time answering one question: how would we know if it works?

It is easy to build something that looks impressive and is quietly wrong. So we built the measuring stick first — a set of requirements taken from the real RFP, each one paired with the page of the real proposal that answers it, or marked as genuinely unanswerable. Then anything we build can be scored against it.

How the measuring stick was made

Figure 3 — four independent annotators, then a human decision
Technical — the two rules that make this trustworthy

1. The golden set may not be produced by the system under test. Requirement recall asks "of the requirements a human finds, how many did the miner find?" If the miner labels the answers, it grades itself and returns a meaningless number near 1.0. All four annotators ran before the production miner existed.

2. Agreement is not verification. Two models agreeing is a better prior, not proof. Every evidence claim had to carry a verbatim quote of 40+ characters, and a script checked that the text is literally on the page claimed. Anything not found was discarded regardless of how confident the annotator was or whether both agreed.

The most valuable rows are the ones with no answer

Twelve of the fifty requirements are verified as unanswerable — the proposal simply does not address them. Both annotators independently discovered why: U.S. Bank never bid the lockbox component. The pricing and personnel tables both read "Lockbox Services: Not applicable", and the word "lockbox" appears six times in 214 pages, all incidental.

Those twelve rows turned out to be the most useful thing in the whole set — see the next section. A benchmark built only from questions the library can answer would have scored 87% and been declared a success, while hiding the failure that actually mattered.

06

Four findings that changed the design

Finding 1 — search scores cannot tell "no answer" from "an answer"

Plain english

The obvious way to detect a gap is: if the best search result scores low, there is no answer. We measured whether that works. It does not.

The proposal is full of banking content. Ask a lockbox question and the search returns plausible banking text that is about the right topic but does not answer the question. It scores well. There is no cut-off that separates the two.

Those medians look separable. They are not: the answerable range bottoms out at 0.408 while the unanswerable range tops out at 0.678. Six of twelve unanswerable questions score above the lowest genuine answer.

What this changed

The prototype had a score threshold doing exactly this job. It would have caught none of these gaps — every one scores above it. We removed the concept entirely. The language model's own judgement decides coverage, and search scores are diagnostic only.

That put the whole safety story on one component, so we measured that component separately before building on it. It refuses 12 out of 12.

Finding 2 — a defect that targets this product specifically

Plain english

Grasph removes near-duplicate search results, which is sensible — nobody wants the same paragraph three times. But it compares only the first ~300 characters, and it does not check whether the two paragraphs came from different documents.

A company's proposals all start the same way: same company description, same mission statement, same certifications. So forty different proposals look like duplicates of each other, and the system quietly keeps one and drops the rest.

Figure 4 — how the same text becomes the wrong citation

We measured it on documents we already had

Two versions of the same Delaware RFP: 1029 of 1053 text chunks (98%) have a near-identical twin. The platform team measured 43% on a pair of annual reports and called it their dominant bug. A proposal library is a far worse case.

It also hits the RFP side. Amended RFPs are near-identical to their originals by definition — so an addendum collapses into the original document, and the amendment silently disappears.

We reproduced it as failing tests in the platform's own test suite, marked so they do not break anyone's build. The fix is small and the platform team wanted a failing test first — this is a good thing for us to contribute.

Finding 3 — the same model, the same words, a weaker rule

Technical

We validated a safety rule — an excerpt from a service the vendor never bid does not answer a question about that service — in a test harness. It held 12/12 across three runs.

Ported into the product with identical wording, it failed: a lockbox question was answered from general-banking text. The cause is structural. chat_completion_json sends everything as a single user message — there is no system role on any provider — while the harness used a system/user split, where behavioural instructions carry more weight.

Worse, it had appeared to pass an earlier run only because that response was truncated and fell to an error path. Two unrelated defects cancelled into a green result. Fixing the token limit for unrelated reasons is the only reason we found it.

Raised, not silently patched. That method is shared with the ingestion extractor, so changing it is not ours to do alone. It is written up in docs/audits/ for whoever owns it, with a suggested additive method that leaves existing callers untouched.

Finding 4 — a language model quietly under-classifies money

Plain english

When two annotators disagreed about what kind of requirement something was, 31 of 33 disagreements ran the same direction — toward the generic "technical" category. And 18 of those were the dangerous kind: one said "a human must write this", the other said "the system can draft it".

Classified "technical" by a capable model "What fees or costs would be charged by your Firm when using a smart safe for currency deposits?"

That is unambiguously a pricing question. Labelled technical, the system would draft an answer about fees. We saw the same effect again later in production code with a different model and a different prompt — which makes it a property of the task, not of one setup.

The fix: never trust one signal

A requirement goes to a human if either the model classified it as commercial/legal or the text contains a commercial marker (fee, rate, insurance, certification, indemnity…). Not both — either.

The two mistakes cost wildly different amounts. A technical item wrongly sent to a person costs a few minutes of review. A pricing item wrongly auto-drafted puts an invented number in a bid. We bias hard toward the cheap error, deliberately.

Phase 3: what we built

A new module inside the Grasph server. Every rule below exists because something was measured, not because it seemed sensible.

Figure 5 — answering one requirement, with each safeguard in place

The four pieces

PieceWhat it doesThe decision inside it
routing.rs Decides if a person must write this Union of model verdict and word-list. Runs before retrieval, so a pricing item can never reach the drafter.
answer.rs Retrieve, judge, draft or refuse No score threshold at all. Citations validated against what the model actually saw. Failures degrade toward a person, never toward a confident answer.
store.rs Saves projects, requirements, matrix rows Tenant name is part of the storage key, so one customer's data is physically a separate range — not a filter applied afterwards.
mining.rs Finds the requirements in an RFP Page-sized windows with overlap, no global cap, whole document scanned rather than a guessed region.

Why mining had to be rebuilt from scratch

Plain english

The prototype stopped after finding 80 requirements. This RFP contains 622. So no matter how good it was, it could never find more than about an eighth of them — the limit was arithmetic, not quality.

Prototype ceilinghard cap at 80
~13%
What we builtmeasured recall
87.5%
Technical

Windows are pages, not character offsets — pages carry provenance for free, so every requirement can cite where it came from. One page of overlap, because numbered items and their sub-bullets straddle page breaks (both annotators reported this independently). A per-window bound of 120 stops a runaway response; there is no global cap, because a global cap silently truncates and that is the exact bug being fixed.

The whole document is scanned. We know this RFP's questionnaire ends at page 64 — but that is a fact about one document, discovered by a human reading it. Hardcoding it would fit the code to a single corpus.

What it measures

12/12unanswerable questions correctly refused — the safety number
8/38answerable ones wrongly refused (better than the reference)

87.5%requirement recall vs 622 human annotations
0.868page recall@3 — the right page reaches the reader

Two honest numbers for mining, not one

Recall is 87.5% against human annotation. But when we checked each of the 78 "missed" requirements against what the miner actually produced on the same page: 34 were present but grouped differently, 43 partially present, and exactly one was genuinely not extracted.

So 87.5% is agreement with human segmentation — the right figure for a compliance matrix, where each row is a discrete thing a person must answer. And ~99.8% is content coverage — the document was read. Both are true; they answer different questions. The annotators themselves split differently from each other (482 vs 468 entries from identical pages), so perfect boundary agreement was never realistic.

Where it is weakest, stated plainly

Five of 82 commercial requirements are not caught by either signal — neither the model nor the word list flags them, so they would be auto-drafted. Two carry real pricing signals we miss ("free access", "annual minimum"); two read as policy questions the annotators judged commercial, where reasonable people would disagree.

The harm is narrower than it first sounds: grounding still prevents invention, so the exposure is unflagged stale fee content — a 2018 fee answer presented without the pricing flag that would make a reviewer look twice. It is recorded as measured residual risk rather than chased, because both safety rules here have already over-fired when strengthened without measuring what they catch.

Two things we only learned by instrumenting it. The mining figure had been estimated at $1.30 from window sizes — the measured number is $0.84, so the estimate was 55% high. And the prompt cache hit rate on mining is zero, where ingestion achieves ~65%: every window sends a fresh prompt, so nothing is reused. That is a concrete, unclaimed saving worth roughly half the input cost.
Mining is not perfectly repeatable. Two runs of the same document produced 740 and 734 requirements — about 1% variance at temperature zero. Small, but it means a single run is not a baseline, and any future comparison needs a variance band rather than one number.

The bugs, and why they were invisible

This is the part most worth reading, because it is the part that generalises. Every significant bug in this project compiled cleanly and passed its unit tests.

BugWhat the code saidWhat was trueFound by
Word matching markers are broad, which is the safe direction rate matched inside "separately" — routed ordinary technical work to humans a test written against my own bias
Evidence size EXCERPT_CHARS = 1800 dead code — text arrived already cut to 300 chars, discarding 62% of it comparing two paths' evidence
Score threshold "validated below the observed minimum" validated against a different scale; silently converted correct answers into gaps comparing two retrievers' scores
API routes compiled, tests green wrong parameter syntax for this framework version — four endpoints matched nothing calling them over HTTP

The one that should worry us most

The score threshold failed by emitting "gap" — which is exactly what an honest refusal looks like. A system that cannot answer and a system that never tried are indistinguishable in the output. It would have shipped as "the knowledge base doesn't cover this", and the review queue would have absorbed the difference invisibly.

And one safety property passed a test run only because two separate defects cancelled out — a truncated response hid a weakened rule. Fixing an unrelated token limit turned a green result red. Had it not been touched, the central safety claim would have shipped as an accident, with the golden set certifying it.

The takeaway for all of us

Unit tests verify a module against its own assumptions. Every bug here was a wrong assumption about how our code meets someone else's — a shared constant, a retriever's score scale, a router's syntax. None of those live in the module under test, so none were catchable there.

What found them, every time, was comparing two independent things and asking why they disagreed.

And one conversation we should have internally

Namespace isolation is already a tracked platform work area. Our multi-tenant work overlaps it in exactly one place — the retrieval gate — and their design deliberately keeps records that carry no tenant label, because structured data predates that label. That is correct for a single-tenant product and a cross-tenant leak for a multi-tenant one.

The question is theirs to answer, not ours to work around: is that rule negotiable, or does multi-tenant retrieval need its own gate that fails closed? Ten minutes of conversation now, versus a merge conflict in a security boundary later.
